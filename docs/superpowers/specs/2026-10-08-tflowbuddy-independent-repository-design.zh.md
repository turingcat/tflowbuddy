# TFlowBuddy 独立仓库设计

[English](2026-10-08-tflowbuddy-independent-repository-design.md) | 中文

## 状态

本迁移方案已在对话中获原则同意，尚未实施。编写实施计划前需审核本设计文档。

## 目标

让 TFlowBuddy 拥有独立的 Git 历史和版本号，同时通过可审核的同步分支导入 DeepSeek Harness 更新。不得通过导入 Git 历史将上游提交作者带入新默认分支。保留版权和许可证署名。

## 仓库迁移

将现有公开仓库从 `turingcat/tflowbuddy` 改名为 `turingcat/tflowbuddy-legacy`。在 `turingcat/tflowbuddy` 创建新的公开非 fork 仓库，默认分支为 `main`。保留旧仓库及其分支、标签、发布、议题和配置，不删除仓库或改写其历史。

以 `v0.1.1` 对应的已提交产品代码作为来源。将获批的迁移文档和工具作为明确的新增内容纳入。排除未提交修改、未跟踪文件、忽略文件、构建产物和凭据。导出跟踪文件，不携带旧 `.git`，保留执行权限和符号链接。上传前检查跟踪文件中的凭据及超过 GitHub 上传限制的文件。

在导出目录创建一个无父提交的初始提交，使用已配置的维护者身份。不复制旧标签、分支或 Git 对象。旧仓库的发布和议题保留在历史仓库，不将它们表示为新项目历史。

在改名任何仓库前准备并验证导出内容。将旧 Git 引用、本地未提交修改和仓库设置备份到导出目录之外。在现有目录旁准备新工作目录，不替换当前工作目录。验证后将新目录的 `origin` 配置为新仓库，将现有目录的 `origin` 配置为历史仓库。现有本地修改仍留在原工作目录。

## 上游同步

使用独立目录拉取 `deepseek-ai/deepseek-harness`，不得将上游引用推送到新产品仓库。同步记录保存上游仓库和上次导入的准确提交。初始记录使用已融入产品快照的经验证上游祖先，而非任意最新上游版本。

每次更新先拉取上游，验证已记录的基础提交和目标提交存在。若目标提交不是基础提交的后代，必须停止，等待维护者明确处理上游历史变化。从当前 TFlowBuddy `main` 创建 `sync/dsh-<date>` 分支。

生成记录的基础提交与目标提交之间的上游文件差异，包含新增、删除、执行权限、二进制文件和符号链接。将差异应用到产品同步分支；基础对象可用时使用三方冲突处理。基础内容缺失或冲突阻止自动完成，不得通过整树替换为上游代码来解决。

将导入的代码提交为新的产品提交，不带入上游父提交或自动附加上游共同作者行。记录来源版本以便署名和重现。在独立目录拉取上游不将其祖先历史导入 `main`。

解决冲突时保留产品拥有的发布版本、品牌、账户集成、分发设置和仓库指令。不得跳过整个包清单：导入适用的依赖和配置修改，再恢复产品版本字段。使用所属工具重新生成受影响的锁文件和生成记录。

合并同步 PR 到 `main` 前运行相关测试并审核差异。在同一导入提交中更新同步记录，使代码与记录的基础版本一起合并。同一目标的第二次同步不得产生上游差异。上次导入后发生的产品修改必须在后续无冲突导入中保留。

## 独立版本

初始产品版本为 `0.1.1`。根清单、Desktop 应用和第一方工作区包共用 TFlowBuddy 版本。后续版本跟随产品发布，不跟随上游标签。导入 dsh 更新不会自动改变产品版本。

新增第一方包使用当前产品版本。版本检查覆盖私有及可发布的第一方包，打包前拒绝版本不一致。版本更新操作能够修复导入造成的不一致，而非在归一化前拒绝运行。

第三方依赖、vendor 包、解释器、Electron、Session 格式及 SQLite schema 版本保留各自含义。本迁移不重命名 `@deepseek-ai/dsh-*` 包或改变 CLI 入口。对上游发布的历史引用仍是事实引用，不是产品发布版本。

产品发布使用 `v<product-version>` 标签。标签检查、已安装 Desktop 标识、内置运行时元数据和安装包文件名必须使用一致的完整版本字符串。

## GitHub 配置和发布处理

迁移前清点仓库设置、Actions 权限、变量、密钥名称、分支规则和发布附件。GitHub API 无法取回密钥值。不得从无关本地服务复制凭据，也不得因为列出密钥名称就声称已迁移密钥。

新仓库初次上传及配置审核期间保持 Actions 禁用。将受支持的 push 和 pull-request 工作流适配到 `main`。没有匹配 runner 时不启用继承的自托管任务，没有所需凭据时不启用定时真实 API 测试，不启用指向上游基础设施的部署工作流。

记录有意停用的工作流及启用条件。保留测试及失败信号，不通过弱化断言或将失败标成成功来完成迁移。现有无关测试失败单独报告。

历史仓库失败的 `v0.1.1` 运行不是成功的产品发布。仓库迁移可以独立于打包修复完成。在单独范围内修复并验证打包失败前，不发布新仓库的 `v0.1.1` 标签。因为历史仓库尚未成功发布 `0.1.1`，新仓库可使用同一版本，但最终标签仅指向新产品历史。

## 验证

- 对比导出文件、执行权限和符号链接与获批快照，仅允许已记录的迁移新增和修改。
- 验证新仓库非 fork、默认分支为 `main`、初始提交无父提交。
- 验证新默认分支不以上游基础提交为祖先，且未推送旧上游分支或标签。
- 测试上游导入中的无冲突修改、产品修改、冲突、新增、删除、二进制文件、版本修改及重复目标。
- 验证版本归一化保留第三方和持久化格式版本、更新新增第一方包并拒绝错误发布标签。
- 运行聚焦的同步测试、版本检查、桌面打包测试、构建、运行时包检查及适用文档检查。
- 验证改名后历史仓库身份不变、新仓库身份不同、远程地址正确、本地未提交文件保持不变。
- 确认 Actions 配置，并以当前 GitHub 证据报告发布任务待完成、失败或成功。

GitHub 贡献者展示可能异步刷新。立即验证 Git 祖先关系，但不承诺所有贡献者界面在上传时立即更新。

## 恢复

导出验证、凭据检查或备份失败时，在仓库改名前停止。旧仓库已改名而新仓库创建失败时，先保留历史名称，待原名称可用且能够安全恢复时再改回。首次上传失败时重试已准备的导出内容，不删除历史仓库。

新仓库已存在而后续验证失败时，保留两个仓库，禁用受影响的 Actions 并报告准确的未完成步骤。不得自动删除仓库、强推改写历史、移动发布标签或覆盖原工作目录。

## 非目标

本迁移不隐瞒代码署名、不重命名所有包、不修复现有桌面打包及其他继承 CI 失败、不迁移全部 GitHub 议题或发布，也不替换上游依赖许可证。这些修改需单独确定范围并验证。
