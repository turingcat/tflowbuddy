# Electron 40 Windows 7 Runtime Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship TFlowBuddy Desktop with Electron 40 on every platform, the pinned community Electron-for-windows-7 runtime on Windows x64 and ia32, one Electron-provided Node runtime per package, and a first-class Windows 7 32-bit packaging workflow.

**Architecture:** Keep the existing `electronDist` packaging seam, but make runtime preparation choose an official npm Electron archive for macOS and a digest-locked GitHub archive for Windows. Use the complete target Electron executable with `ELECTRON_RUN_AS_NODE=1` for dsh, pnpm, CLI wrappers, and command management; retain only shell wrappers in `runtime/bin`, never a second Node executable. Extend target, upload, update, CI, and test matrices with `win-ia32` while allowing a Windows x64 host to prepare both Windows architectures.

**Tech Stack:** Electron 40.10.6 (official macOS npm artifact), Electron-for-windows-7 v40.2.0 (Windows archives), Electron Builder 26, TypeScript/tsx, Vitest, pnpm, GitHub Actions.

**Spec:** `docs/superpowers/specs/2026-10-05-electron40-win7-design.md`

## Global Constraints

- Windows targets are `win-x64` and `win-ia32`.
- Windows uses community Electron-for-windows-7 `v40.2.0`.
- `dist.zip` SHA-256 is `ed4ebb022624ae38f764fcfc1dc1ce30fe2145298975d4c90e8d95412deeadea`.
- `dist-x86.zip` SHA-256 is `0a7560eae08360a6181515e0f20fd4c8f26a471c5118a427958a1d5974b767e5`.
- macOS uses the official npm Electron 40.x package pinned to `40.10.6`.
- The dsh process runs through the packaged Electron executable with `ELECTRON_RUN_AS_NODE=1`.
- Each package contains one Node runtime: Electron's embedded Node; `runtime/bin` may contain only launcher scripts.
- A Windows x64 host may prepare `win-x64` and `win-ia32`; a Windows ia32 host may prepare only `win-ia32`.
- Windows 7 compatibility is not a security-support promise and must be stated in release documentation.

## Review Focus

- A cached or newly downloaded community archive has altered bytes; preparation must re-hash it and fail before extraction.
- A target string or host architecture is invalid; target parsing must reject it before any packaging subprocess starts.
- The ia32 package accidentally receives x64 native modules; package preparation must select ia32 artifacts or fail with the dependency name.
- A runtime tree contains a copied Node executable; packaging checks must reject executable Node files outside the Electron distribution and launcher scripts.
- The update/upload path omits `win-ia32`; target-specific records, URLs, artifact names, and CI publication must remain distinct.
